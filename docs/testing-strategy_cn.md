# Nola Testing Strategy 中文版

## 目的

Nola 的质量不只是正确性，还必须保护温柔体验、低认知负担、本地数据安全和跨平台可持续性。

## 测试原则

- 在靠近变更的位置验证最小单元。
- 把 ADHD 友好体验当作质量要求。
- 对领域逻辑优先使用可重复测试。
- 对语气、视觉负担和平台特定提醒使用人工检查。
- 没有新鲜证据，不声明发布就绪。

## 测试层级

| 层级 | 目的 | Nola 示例 |
| --- | --- | --- |
| 单元测试 | 验证隔离领域逻辑 | 任务状态规则、随机启动选择、能量筛选 |
| 集成测试 | 验证连接行为 | SQLite 持久化、提醒规则存储、状态恢复 |
| UI 测试 | 验证用户流程 | 捕捉任务、打开今日视图、转换灵感条目 |
| 平台测试 | 验证原生行为 | Windows/macOS 通知、托盘、文件备份 |
| 可访问性测试 | 验证包容性使用 | 键盘导航、焦点可见性、对比度 |
| 产品 QA | 验证 ADHD 友好性 | 文案语气、视觉平静、低压状态 |

## 文档类变更验证

对于执行体系工作：

- 必需文件存在。
- 本地 Skills 有合法 frontmatter。
- 替换 Skill 时旧名称已移除。
- 没有创建业务源码或 package 文件。
- 跨文档引用指向真实文件。

## 后续实现验证

| 变更类型 | 最低证据 |
| --- | --- |
| 共享领域逻辑 | 单元测试 |
| SQLite schema | 迁移和持久化测试 |
| 提醒行为 | 规则单元测试 + 平台人工检查 |
| 桌面端 UI | UI 流程验证和可访问性检查 |
| 设计 tokens | 对照设计系统进行视觉检查 |
| 发布构建 | Windows 和 macOS 冒烟检查 |

## ADHD 友好 QA 清单

- 界面是否避免严厉紧迫感？
- 下一步是否清楚且足够小？
- 用户能否在未完成后无羞耻地恢复？
- 屏幕是否视觉平静？
- 主要操作是否无需密集说明也能找到？
- 随机启动是否像支持，而不是命令？

## 回归重点

实现后保护这些流程：

- 快速捕捉任务。
- 快速捕捉灵感箱条目。
- 重启后数据仍然存在。
- 显示今日任务。
- 选择随机启动建议。
- 创建并投递提醒。
- 将任务标记为完成或暂停。

## 发布证据

发布说明应包含：

- 执行过的命令
- 人工 QA 场景
- 平台检查
- 已知风险
- 回滚或恢复计划
